# TEST HMI 通信与分类显示实现

更新：2026-11-08；本文件对应本目录指定 HMI 工程，不是固件仓库 TEST/ 副本。无 mutex 轮询版本的 ARM C++11 编译/链接与主机回归已通过；本次未部署，真实屏端仍待验收。

## 代码位置与 UI

- src/HmiRecord.h：HmiRecord/HmiEvent 和流式 HmiParser，使用调用方提供的单调毫秒时钟。
- src/hmi_codes.h：90 码共享映射，原九色码保持原序，追加原8形状白色73..80、圆锥10色81..90。
- src/hmi_protocol.h：与 MCU Core/Inc/hmi_protocol.h 保持完全相同的 CRC 实现，固件自动回归会校验两份字节一致。
- src/HmiApp.h：commandHistory 改为 vector<HmiRecord>，存储 code/ID/record_sequence；previewCode 为临时预览，独立于生产历史。
- src/pages/Wcmn.h/.cpp：串口 COM2 不变；接收线程零等待读取与解析，每批通过 AsynWorker 回到 UI 线程更新状态和列表。
- src/pages/Frm02.h/.cpp：syncCommandHistory/appendRecord 从统一表重建列表，显示固件 ID，重开页面不重新编号；最多保留 256 条，淘汰同步到 UI。预览为独立临时行，不进入 history。

已有8张WHITE黑底白色资源，新增10张CO圆锥资源（白色黑底）；lib/、页面布局、原 72 张图片及图片路径均未修改。生成的 createParts 保持原样，新增声明/逻辑置于 CUSTOM 区或独立应用头文件。记录为内存历史，无断电持久化。

## 新分类帧

固定 22 字节：F0，10 个数据字节各拆为高/低半字节并编码为 0x80|n，F1。中间 20 字节全部为 0x80..0x8F，旧屏不会把元数据当 1..72 指令。

| 解码字节 | 字段 |
|---|---|
| D0 | version=1 |
| D1 | type=1 分类完成记录，type=2 新会话清空 |
| D2..D5 | uint32 小端 record_sequence；type1 从 1 递增，type2 为 0 |
| D6 | code 1..90；type2 为 0 |
| D7 | 固件 ID 1..6；type2 为 0 |
| D8..D9 | D0..D7 的 CRC16/CCITT-FALSE，低字节先发 |

CRC：poly=0x1021、init=0xFFFF、refin/refout=false、xorout=0；ASCII 123456789 校核为 0x29B1。

seq=1/code=19/ID=3 完整示例：

```text
F0 80 81 80 81 80 81 80 80 80 80 80 80 81 83 80 83 86 8F 8E 8D F1
```

新会话：

```text
F0 80 81 80 82 80 80 80 80 80 80 80 80 80 80 80 80 80 8E 81 86 F1
```

HOST 初始化发送一次 type2；DEBUG 不主动清历史。type1 仅在释放流程成功完成后发送一次；上位机重发只补状态，不重发 HMI。记录已发送后停靠失败，记录保留而 HOST 收 FAILED。

## HMI 处理与限制

HmiRecord.h 在单调时钟 200 ms 超时下解析分包、连续包和噪声；长度、编码、CRC、版本/type/范围无效即丢弃，不把坏帧数据回灌成预览。Wcmn 的串口回调运行在 COM2 接收线程：`readData(bytes, 0)` 零等待取数、解析成事件后，每批通过一次 `AsynWorker::onFinished` 跳到 UI 线程执行 `applyEvents`，由 UI 线程更新 `串口` 变量、`commandHistory` 和 Frm02 列表并只重建一次。回调本身不读写任何 UI 状态；无 STTTimer、无轮询、无应用层 mutex。页面退出先置 `active=false`，再关闭串口，已排队的异步批次直接丢弃。

HmiApp::commandHistory 保存 code、ID、record_sequence，最多 256 条；Frm02 从统一历史重建列表，页面重开不重新分配 ID。每件材料可追加同 code 的新记录，显示如“ID:3 指令:19 五棱柱-红”。ID 只来自固件；第七新类循环 ID1，原第一类仍为 ID1。

HAL_UART_Transmit 成功仅表示 MCU 本地发送完成，不代表屏端收到/渲染。扩展帧只发送一次，没有 ACK、重发、可靠清屏握手、掉线补发、会话恢复或断电历史持久化。HMI 晚启动/重启可能丢旧历史，但后续每条记录自带真实 ID。HMI 发送错误只计数，不重抓/重释放。

## 2026-11-02：回调驱动 + 一次 UI 跳转（当前方案）

公共页注册启用。Wcmn 不再创建 STTTimer：`wMCom3_vch_cb` 在 COM2 接收线程执行 `readData(bytes, 0)` 零等待读取，交给 `consumeSerial()` 解析，每批事件通过一次 `AsynWorker::onFinished` 跳到 UI 线程执行 `applyEvents()`。变量写入、`commandHistory`、`previewCode` 与 Frm02 列表只在 UI 线程改动；解析器和 `active` 之外的接收侧状态只在接收线程改动，因此没有应用层 mutex、队列或轮询。

选型依据：SDK 把线程职责写死在 `IAsynWorker` 文档里（`invoke` 禁止 UI 操作，`onFinished` 可做 UI 操作），串口回调不属于 UI 线程；定时器方案虽然也成立，但实测 `STTTimer::onEventHandler` 只接受 code=31（`Event::READY`），传 `Event::VALUE_CHANGED` 会被静默忽略，回调一次都不会执行。改为回调驱动后显示延迟从“最多一个轮询周期”变成“一次异步往返”，也不再依赖定时器语义。

限制：`AsynWorker::start()` 失败时该批事件被丢弃并计入 `droppedUpdates`，不做跨线程直接刷新的降级。记录按批跳转，理论上多批并发完成时顺序由 SDK 异步完成顺序决定；生产节拍（每件数秒）远大于一次往返，尚未观察到乱序。持续满速输入、UI 长时间阻塞仍可能溢出 SDK 接收缓冲。200 ms 解析超时按读取时间判断，不能还原 UART 实际到达时间；不承诺无丢包或可靠握手。

验证：`python -X utf8 tools/selftest_hmi_worker.py` 用真实 Wcmn.cpp 方法体与 SDK 替身覆盖：未 onLoad 不读串口、零等待读取、分包/200 ms 超时、CRC 拒绝、一批事件只跳转一次且只在 UI 线程改状态、历史上限 256、缺页时打开 Frm02、dispose 丢弃已排队批次、`start()` 失败不越权刷 UI。`python -X utf8 tools/build_hmi.py` 通过且无警告，应用库不再导入任何 STTTimer 符号。Windows 模拟器用真实 22 字节帧注入 `consumeSerial`，三帧按序落到列表（ID:3 指令:19 / ID:1 指令:1 / ID:6 指令:72）。

本轮没有覆盖工程 Release/libbootpanel.so。候选库在固件仓库 `MDK-ARM/MechanicalVerify/hmi_arm/libbootpanel.so`；真实屏端启动与收包仍待实机验收。修改前备份：`MDK-ARM/MechanicalVerify/hmi_polling_backup/20261102-202935/`。
