# TASK TIMEOUT 排查记录

日期：2026-11-08。仅排查并保存证据，未修改任务预算、运动参数或 Jetson 服务。

## 结论

本次故障发生在释放完成后的回 HOME 阶段，整任务的 18 秒预算耗尽。用户确认现场为“已经释放，回 HOME 途中”。Jetson 日志中的首笔任务在 ACK 后 18.073506 秒收到固件 FAILED，与固件全局截止时间相符。

当前释放点为 `(215,105)`，HOME 为 `(0,0)`，`APP_PARK_AFTER_TASK=1`。升降、托盘、去取料、吸取、去释放、释放和回 HOME 共用一个 `APP_HOST_TASK_BUDGET_MS=18000U`，不会在释放完成后重新计时。

## 日志证据

从 Jetson 的 `journalctl -b -u huatai-vision -o json` 获取日志。启动后的墙上时钟有调整，因此耗时采用 journal 的 `__MONOTONIC_TIMESTAMP`，不依赖日期时间校准。

| 事件 | 启动后单调时钟 / 秒 |
|---|---:|
| 发送 SEQ=1、CMD=79、X=178、Y=111 | 162.695189 |
| 收到 ACK | 162.709917 |
| 收到 FAILED | 180.783423 |
| ACK 到 FAILED 的间隔 | **18.073506** |

原始抓取帧：`aa 55 01 01 4f b2 00 6f 00 71`。识别浮点坐标为 `(177.9,111.1)`，线上整数坐标为 `(178,111)`。

本次保存的日志中只有这一笔任务收到 ACK；之后 89 笔任务无 ACK 即收到 FAILED，发送到失败回包的中位时间为 14.413 ms。这与固件在超时后使原点失效、后续任务在开始动作前被拒绝的路径一致。

原始日志：`MDK-ARM/MechanicalVerify/task-timeout-20261108/journal-current-boot.jsonl`。Jetson 证据副本位于 `/home/jetson/.cache/huatai-task-timeout-20261108/`。

## 代码路径

- `Core/Src/app_controller.c`：在 ACK 前调用 `AppRuntime_BeginTask()`，回 HOME 完成后才检查终态并调用 `AppRuntime_EndTask()`。
- `Core/Src/app_runtime.c`：从任务开始累计 `HAL_GetTick()`，达到 18000 ms 即过期。
- `Core/Src/app_controller.c`：释放成功后先发送 HMI 记录，再回 HOME。因此屏幕有分类记录与任务最终 FAILED 可以同时出现。
- 超时后调用 `XY_Stop()`、`Tray_Stop()`，使 XY 和托盘原点无效，并显示 `TASK TIMEOUT`。后续任务因原点无效返回 FAILED。
- Jetson 的 `--pick-timeout` 默认为 20 秒；本次实际收到了固件 FAILED，上位机自身的 `pick timeout` 并非本次触发源。

## 当前参数下的耗时估算

按固件使用的加速模型：300 RPM、ACC=20、每 RPM 加速间隔 `(256-20)*50 us`，从静止到 300 RPM 的单边爬升约 3.54 秒。对短行程采用对称三角速度曲线，较长行程采用梯形曲线，估算首笔任务如下。

| 动作 | 估算 / 秒 |
|---|---:|
| `(0,0)` 到取料 `(178,111)` | 4.52 |
| 取料到释放 `(215,105)` | 1.74 |
| 释放到 HOME `(0,0)` | 4.76 |
| 首次抬杯、降杯、取料后抬杯 | 3.00 |
| 吸取 1500 ms、释放 2000 ms，另各 200 ms | 3.90 |
| 三次 XY 后稳定等待，各 100 ms | 0.30 |
| 合计 | **约 18.23** |

首笔新类别为 ID1，托盘目标为 0°；上述合计没有计入额外转盘运动、串口事务、反馈轮询和显示开销。该表是根据当前参数的理论估算，不是电机或各阶段的实测耗时；现有协议只回 ACK/终态，不能从日志直接读出每阶段耗时。但它说明当前完整路径缺乏 18 秒内完成的余量，且与现场回程超时一致。

此前 HOST 自动测试将 XY、升降和真空动作替换为即时返回的模拟函数，能验证状态与超时保护逻辑，不能据此证明真实完整周期在 18 秒内完成。

## 后续处理依据

应按完整路径（包含回 HOME 与托盘）的实测最长耗时设置固件任务预算，并同步设置更长的 Jetson 等待时间，为停止和终态回包留余量。仅修改 Jetson 的 20 秒超时不会改变固件的 18 秒截止时间。也可在机械验收后优化运动速度/加速度，但不应为了规避超时跳过既定安全等待或取消回 HOME。

若需要区分后续不同故障，应记录每阶段耗时及超时阶段；当前 `TASK TIMEOUT` 会覆盖阶段性的显示文本。现有超时会使原点失效，恢复时必须按当前机械位置正确重新建立软件原点，不能靠反复发送任务解除。


## 后续变更：整任务等待统一为 24 秒

按用户要求，将固件 `APP_HOST_TASK_BUDGET_MS` 改为 `24000U`，Jetson 的 `--pick-timeout` 默认改为 `24.0` 秒。本文件前述 18/20 秒数值是故障发生时的配置与日志证据。24 秒覆盖完整抓取、释放和回 HOME；单笔 UART/电机事务保持原有故障检测。
